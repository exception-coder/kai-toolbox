# Forge 产品与交互哲学

Forge 围绕项目、任务及其证据组织 AI 开发工作。用户应能看清正在操作哪个对象、AI 根据什么执行、当前结果是什么，并能从失败处继续。增加一种能力，不应默认增加一套导航、对象列表或配置副本。

本文是项目级设计约束，由 `AGENTS.md` 路由；[AI 编程结构规范](ai-coding-architecture.md) 定义上下文分层，OpenSpec 定义具体行为，源码与运行验收证明实现。本文不替代它们，也不把当前页面形态永久固定。

## 结构与权威

| 层次 | 唯一职责 | 落位 |
|---|---|---|
| 项目入口 | 告诉 Agent 何时读取哪些规则 | 根 AGENTS.md |
| 产品哲学 | 目标、取舍、约束与例外 | 本文 |
| 工程上下文 | Instructions / Knowledge / Specification / Code Intelligence / Capability / Implementation 分工 | ai-coding-architecture.md |
| 行为与决策 | 场景、对象、状态、接口、例外和验证任务 | openspec/specs 与 openspec/changes |
| 视觉语言 | 项目组件、tokens、布局约束及参考画像 | frontend/src/components/ui、index.css、quiet-luxury-ui、design.config.json |
| 验证证据 | 实际测试、浏览器与运行结果 | 对应 change 的 tasks 及原始验证输出 |

设计画像为参考材料；本项目明确约束优先于候选画像。没有个人设计注册表的开发者仍能通过仓库内本文、组件和 tokens 完成工作。不要把个人路径或技能缓存作为项目运行依赖。

## 稳定原则

| ID | 原则与可执行约束 | 适用范围与例外 | 验收问题 |
|---|---|---|---|
| OBJ-01 | 以对象为入口。已经选定项目、任务或记录后，操作继承其唯一身份，不再要求重复选择。 | 单对象操作；真正跨对象比较、批处理可有独立工作区。 | 执行对象是否清楚？是否复制第二份同目的列表？ |
| NAV-01 | 动作依附对象，页签组织稳定的信息视图。后端多一个接口不等于前端多一个页签。 | 导航和页面分区；长流程、独立检索或可分享目的地可使用页面。 | 新入口承载的是对象、视图还是动词？离开当前对象是否必要？ |
| CTX-01 | 操作前后保持上下文。覆盖层关闭恢复触发器焦点，保留筛选、列表位置、对象和适用草稿。 | 弹框、抽屉、返回导航；对象删除或权限变化时转到有效恢复位置。 | 关闭后用户能否接着工作，而非重新定位？ |
| DENS-01 | 信息密度由任务优先级决定。重复状态、实现标签和低频工具渐进展示，核心对象和操作保持可发现。 | 桌面和移动端；必要对照信息不能为省空间隐藏。 | 首屏展示了什么？缩小按钮是否被误当作空间优化？ |
| FEED-01 | 操作形成开始、进行中、结果、恢复的闭环。失败、无变化、部分成功与结果未知必须如实区分。 | 查询、保存、生成、安装、推送；普通焦点和键入不需要额外弹框。 | 有没有把请求完成、窗口关闭或日志输出当作业务成功？ |
| AI-01 | AI 使用与人相同的对象身份、公共业务能力和权限边界，不建立平行项目配置、状态或事实源。 | AI 集成与自动化；适配器可不同，业务规则和授权不可绕过。 | AI 是否知道对象、范围、输入证据与执行限制？ |
| EVID-01 | 区分规格、代码推断与运行事实。Graphify 是代码事实，OpenSpec 是行为依据，构建或运行成功需真实验证。 | AI Ready、知识探索、状态展示、交付；证据缺失必须可见。 | 是否把“已生成”“已发起”或“AI Ready”当成正确性证明？ |
| CTRL-01 | 自动化应可理解、可追踪、可恢复；具备授权才执行影响外部的动作，禁止以关闭窗口暗示撤销已发出的请求。 | Agent 执行及写操作；需要长时间后台运行时应有持久任务与结果入口。 | 用户能否确认实际目标、结果及安全重试方式？ |
| IDEM-01 | 可重复触发的创建、切换、提交和恢复动作必须先解析稳定业务身份，查询并复用已有结果；超时、重连、刷新或重复点击不得默认制造第二份对象。 | 用户明确要求副本，或目标对象已删除、失效且界面明确说明重建时例外。 | 相同意图执行两次会得到同一对象/结果吗？幂等键是否跨刷新持久化？ |

## 选择页面、页签还是覆盖层

按下面顺序判断，而非先选组件再寻找理由。

| 用户需要 | 默认承载方式 | 应避免 |
|---|---|---|
| 浏览或查找多个项目 | 唯一项目列表，搜索/筛选 | 为每个动作再建一份项目列表 |
| 对当前项目做一次有界操作或查看补充信息 | 对象行按钮或更多菜单 → 弹框/抽屉 | 切换全局页签后再次选择同一项目 |
| 查看同一对象的稳定信息类别 | 对象详情中的页签/分区 | 把刷新、Push、导出等动词各做成页签 |
| 同一内容的筛选或显示形式切换 | 筛选器或视图切换控件 | 伪装成新的业务目的地 |
| 持续编辑、大量对照、复杂步骤或可分享独立任务 | 有明确对象范围的页面/工作区 | 将复杂工作塞入多层弹框 |
| 跨项目批量管理或比较 | 具备跨对象价值的独立工作区 | 只有第二个项目选择器，却没有批量或对照能力 |
| 管理全局资源、目录或环境 | 全局设置/管理视图 | 强行归属某个项目，制造错误作用域 |

弹框与抽屉都是覆盖层：弹框适合聚焦任务，抽屉适合依附对象的补充浏览或编辑。两者均需可见标题、关闭入口、焦点管理和适用的未保存保护；页面是否合适取决于任务，而非接口数量。

## 覆盖层与异步操作契约

- 标题标明对象，路径、编号等辅助信息用于消除同名歧义；主列表按钮与详情链接不得嵌套。
- 打开后焦点进入覆盖层，Tab/Shift+Tab 不落到背景，关闭后回到触发器；查询失败仍可关闭和重试。
- 内容限高、可滚动，窄屏不横向溢出，关闭入口和末行操作可达。不能用层层弹框弥补信息架构问题。
- 写操作进行中防止重复执行。若关闭会丢失唯一结果入口，应明确等待提示并保护当前上下文；只有具备持久后台任务和重新进入能力时，才允许离开后继续。
- 关闭弹框不等于取消后端操作。超时或断连应提示先核对实际结果，不假定未执行。
- 一次局部结果刷新不清空整个页面的筛选或草稿，不因对象变化把旧结果显示到新对象上。

## 本次落地案例

项目库保留“全部项目”作为唯一列表。每个项目行的 Git 按钮打开该项目的 Git 操作弹框；关闭后回原列表。顶层 Git 工作区页签及其重复项目选择器移除。待 Commit/待 Push 可以保留为弹框内同一 Git 对象的两类数据视图。

全局目录设置、环境管理和 AI 上下文诊断具有不同作用域，不因本次反馈一并改成项目弹框。未来若出现真实的多项目 Git 批量或比较需求，应重新评估独立工作区，并在对应 OpenSpec 说明跨对象价值。

## AI 实施与审查门槛

新增或调整导航、对象操作、覆盖层及 AI 执行流程前，Agent 必须在对应 change 的 design 中列出适用原则 ID，以及下面四项结论：

1. 主对象是什么、唯一身份是什么；能力是否复用了现有列表和公共服务。
2. 选择页面/页签/覆盖层的理由；相较现状减少或增加了哪些定位和返回步骤。
3. 加载、成功、失败、结果未知、关闭、重试和适用草稿的处理。
4. 键盘、焦点恢复、窄屏和实际业务结果的验证方式；例外需说明原因、风险及复核条件。
5. 稳定业务身份与幂等键是什么；重复点击、重连、刷新、切回以及并发请求是复用、拒绝还是明确创建副本。

这些是设计与验收要求，目前不是自动静态检查器。不得声称仅通过文档结构校验就证明交互合规；实际验证结果记录在 tasks，不复制成第二套设计正文。

## 来源与演进

- 2026-09-13 用户明确指出项目列表与 Git 页签重复选择对象，并要求在项目中沉淀约束。OBJ-01/NAV-01 为本项目据此采纳的决策，不宣称行业标准禁止所有动作页面。
- 2026-09-21 Codex Auth 往返切换曾重复创建会话并重复交接，暴露出仅保留上下文而未约束重复执行的问题；据此新增 IDEM-01，并要求幂等身份持久化而非依赖浏览器临时状态。
- 结构参考 yoooni-one 的 AGENTS、docs/ai-coding-architecture.md、docs/development/frontend-component-conventions.md 和 design.config.json。两项目共享分层方式，不复制业务规则。
- [Carbon Tabs](https://carbondesignsystem.com/components/tabs/usage/) 将页签用于同一上下文的相关内容分类；[WAI-ARIA Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) 提供模态语义与键盘、焦点规则。查阅于 2026-09-13。
- 本次实例与回归证据见 [anchor-project-git-actions](../openspec/changes/anchor-project-git-actions/design.md)。个人设计注册表只记录本地范围偏好，不自动晋升全局 CORE 或 ESTABLISHED。

新增原则须给出实际问题、适用范围、反例和验收方式；修改原则保留稳定 ID，在对应 OpenSpec 记录理由与迁移影响。先验证具体页面，再考虑推广，不以单次截图审美覆盖整个产品。
