## 业务定义

每个下载任务在正式下载前，都会先做一次"直连 vs 代理"链路择优，而不是固定走某一条：

- **参与 race 的两条链路**：一条是"直连"，一条是当前检测到的"代理候选"（可能没有）。两条链路各取一小段样本数据，同时测出各自的吞吐速率（字节/秒）和首字节响应时间（TTFB）。
- **择优规则**：
  - 若两条链路都探测成功：吞吐量更高的一方胜出；吞吐量相同时，TTFB 更低的一方胜出。
  - 若只有一条链路探测成功：直接采用这一条，不比较。
  - 若两条链路都探测失败：任务判定为"两端均不可达"，直接失败，不进入下载阶段。
- **主/备链路语义**：胜出的一方记为「主链路」，用于分片下载；另一方如果当时也探测成功，则记为「备用链路」——当某个分片在主链路上下载失败时，可以切到备用链路重试，而不是直接判定整片失败。
- **代理候选从哪来（优先级从高到低，取第一个命中的）**：
  1. 工具箱内显式配置的代理；
  2. 环境变量（`HTTPS_PROXY`/`HTTP_PROXY` 及其大小写变体、工具箱自定义变量）；
  3. JVM 系统属性形式的代理配置；
  4. 操作系统级代理设置（如 Windows 系统代理注册表项）。
- **不缓存决策**：每次创建任务都会重新做一次探测和 race，不复用上一次的判断结果，确保用户临时开关代理/VPN 后新建任务能感知最新情况。

## 适用范围 / 边界

- Race 只发生在任务**创建（kickoff）时**，以及"暂停后从未成功探测过路由"的续跑场景。
- 若任务是**从已有路由结果的暂停状态恢复**（断点续传），则沿用当时决出的主链路，只对备用链路重新探测一次可用性（因为用户可能在暂停期间开/关了代理），不重新对主链路做 race。
