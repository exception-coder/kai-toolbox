## 业务定义

在 Vibe Coding（`claude-chat`）里，"会话"不是一次性的问答，而是一个**跟工作目录绑定的持久实体**，代表"我在这个项目目录下，跟 AI 就这件事持续聊/持续改"的一段完整过程。它有以下几层业务含义：

- **与工作目录强绑定**：一个会话固定对应一个工作目录（cwd），会话存在的意义就是"在这个目录下"进行的一连串交流和改动；换目录即换会话，而不是在同一个会话里切换项目上下文。
- **引擎可切换、但会话是同一个"人格"**：一个会话在其生命周期内可以先后使用不同的 AI 引擎（如切换到另一种执行方式），但用户视角里这仍然是"同一个会话"——标题、所属目录、历史沿革不变，只是执行它的引擎变了。
- **每个引擎各自持有独立的可续跑记忆，互不覆盖**：会话切换过引擎之后，之前用过的每个引擎各自保留自己的执行上下文句柄，下次再切回某个引擎时，能接着该引擎自己的历史续跑，而不会因为中途换过引擎就丢了其中一个的记忆。
- **可分组、可归属**：会话可以被用户自定义归到一个分组下，便于按用途或项目归类管理，这个归类是跨设备可见的持久设置，不是本地临时状态。
- **第三方网关可覆盖官方入口**：会话可以指定走某个兼容网关而非官方默认入口，这是会话级别的配置，不同会话可以各自选择不同的入口。

这套定义背后的业务动机是：开发者的一次"跟 AI 结对做一件事"往往会跨越较长时间、可能中途想换一种 AI 试试效果，但不希望因此丢失上下文或另起炉灶——"会话"就是承载这种连续性的领域概念。

## 适用范围 / 边界

- 同样适用于 `claude-chat-stable`（Vibe Coding 稳定版）——两者复用同一套会话概念与后端，稳定版只是面向更保守使用场景的另一个入口，会话语义不变。
- 不适用于各"XX 需求开发"前门模块（`erp-dev`/`kai-dev`/`new-devmodule`/`project-workspace`/`srm-dev`）本身——那些模块只负责组织触发语、把用户交给这里描述的会话来执行，前门模块自己不持有这个"会话"概念。
- 特例：一个全新会话在第一次使用前不涉及"引擎切换"和"续跑"，这两条只在会话经历过至少一次引擎切换或一次中断之后才有意义。

## 备注

- 口径来源：kai-toolbox 代码调研起草（会话持久化结构里对工作目录、引擎、多引擎句柄、分组、第三方入口等字段的设计），待 owner 核实。
- 易混点：不要把"引擎"理解为会话的固有属性——会话本身是引擎无关的容器，引擎只是"当前用谁来执行这个会话"的可变选择。
