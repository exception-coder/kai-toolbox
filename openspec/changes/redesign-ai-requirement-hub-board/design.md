## Context

`ReqPoolPage` 当前在桌面端使用 `<table>` 展示需求、负责人、交付进度和风险，移动端另用 `MobileRequirementCard`。现有数据、筛选、批量选择、详情抽屉和文档操作已完整，问题集中在主视图的信息组织。Graphify 将入口定位到 `ReqPoolPage.tsx`、`ReqPoolSections.tsx`、`reqpoolPageModel.ts`；源码核验显示表格位于 `ReqPoolPage.tsx:377-440`，现有命令均由页面 hooks 提供。

约束：不改变 API、需求状态机或现有详情/文档流程；复用主题 token；避免全盘卡片化、厚重阴影和装饰渐变；与工作区已有无关修改隔离。

现有实现已落在 `RequirementBoard.tsx` 与 `ReqPoolPage.tsx`。本轮在该组件边界内继续演进，避免把 Mission Control 逻辑堆回页面。

## Goals / Non-Goals

**Goals:**

- 用当前焦点建立“今天什么最重要”的主阅读路径。
- 任务不超过五项时避免渲染大量空阶段列；超过阈值后保留完整阶段看板。
- 用基于现有状态的短活动流表达 AI 当前动作与下一步，不伪造新的后端事件。
- 用独立便签降低横向字段阅读成本，同时保留现有证据和风险信息。
- 桌面与移动端共享同一看板组件和信息规则。
- 保留加载、空列、筛选无结果、批量选择和详情恢复路径。

**Non-Goals:**

- 不新增拖拽、排序写回或状态更新 API。
- 不改领导视图、详情抽屉、PRD/TDD 工作流或后端数据。
- 不引入新的 UI 或拖拽依赖。

## Decisions

### 使用自适应 Mission Control，而不是始终铺开六列

状态仍是稳定业务事实，顺序为待受理、澄清中、已准入、交付中、已交付、已归档。根需求不超过五项时突出一个确定性焦点并用阶段计数条保留全局上下文；超过五项时呈现六列完整 Kanban。这样既避免稀疏数据下的空列浪费，也不牺牲高密度管理能力。

替代方案是按 NOW/CLARIFY/PLAN/PARK 分列，但它把建议误当成流程状态，因此不采用。

焦点优先级为交付中、高风险/待补充、建议投入、最近更新，规则完全由现有数据确定。活动流只翻译 PRD/TDD/代码后台状态、当前阶段和缺口，不宣称不存在的执行事件。

### 便签是独立对象，页面分区保持平面化

每张便签使用轻边界、克制圆角和极轻悬浮反馈；阶段列只用标题、计数、细分隔和轻微色调，不做 Card 套 Card。信息顺序固定为标题、摘要、项目模块、交付证据、负责人/期限、风险。

### 保留点击详情和显式复选框，不加入拖拽

点击便签打开现有详情抽屉；复选框继续支持批量删除。状态变化仍由既有业务操作完成。若未来加入拖拽，必须同时提供单击/键盘可达的移动菜单，满足 WCAG 2.2 拖拽替代操作要求。

### 响应式按模式重排

Mission Control 在窄屏按焦点、活动、最近任务单列排列；完整看板以固定最小列宽横向滚动。页面顶部状态带、筛选和操作可换行，但不压缩任务对象。

详情抽屉在窄屏占满视口，元信息从双列改为单列，Agent 名称、运行状态和引擎分行展示，底部操作纵向铺满并保持至少 44px 触控高度。桌面端从 `sm` 断点恢复紧凑双列与横向操作，避免把桌面缩放当作移动端方案。

## Risks / Trade-offs

- [六列导致横向滚动] → 给每列稳定宽度、清晰滚动边界，并在窄屏默认从最前阶段开始。
- [便签信息过密] → 只展示每类信息的一条主信号，完整内容进入详情抽屉。
- [归档列占用空间] → 保留其可见性以反映完整生命周期；空列仍展示轻量空态。
- [现有字段配置语义弱化] → 字段开关继续控制便签内部对应信息，密度设置控制便签间距。

## Migration Plan

1. 新增纯展示 `RequirementBoard`，复用页面现有回调与数据。
2. 用看板替换统一工作台的移动卡片和桌面表格分支。
3. 补充分组和阶段顺序测试，运行前端测试、类型检查、构建及 Forge 门禁。
4. 在真实浏览器检查 1440px 与 375px，并验证打开详情和筛选无结果。

回滚只需恢复 `ReqPoolPage` 的原表格渲染并删除新增看板组件；无数据迁移。

## Open Questions

无阻断项。拖拽状态流转作为后续独立变更评估。

## AI-native lifecycle projection

主视图不再把规格、计划、代码和交付并列为业务 Stepper。用户生命周期固定为草稿、已就绪、执行中、待确认、已完成；规格、计划和代码保留为第二层可操作证据。现有后端状态保持兼容，前端结合需求状态、进度 Agent 运行状态和代码分析得分做确定性投影。进度 Agent 完成且代码覆盖达到 90% 时进入待确认，最终完成仍只由用户确认后的 `DONE` 状态表达。归档作为生命周期外的历史状态保留。
