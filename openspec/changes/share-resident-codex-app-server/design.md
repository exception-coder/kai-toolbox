# 常驻 Codex App Server 设计

## 依据和适用范围

OpenAI 的 [App Server 架构说明](https://openai.com/index/unlocking-the-codex-harness/)和[客户端协议](https://learn.chatgpt.com/docs/app-server#core-primitives)支持长连接上的多线程与双向 JSON-RPC。Forge 当前原生版本为 0.171.0，同版本生成的 `ThreadResumeParams` 说明，已运行的线程会被重新加入。不能据此假定已加载线程会重读进程配置，或上一轮完成后原生线程已释放写入权。选择原生 stdio 和生命周期协议。Forge 只补授权分组、路由和恢复，应用现有队列与回执。涉及 OBJ-01、AI-01、FEED-01、EVID-01、CTRL-01、IDEM-01。

## 生命周期和边界

- 进程归属依据账号及实际进程级配置。线程继续使用自己的工作目录、工具策略和回执。复用前核对原生版本对线程配置的实际行为。策略变更、隔离场景和执行通道切换都要进入归属核对。
- 连接负责单一输入输出读写、请求编号和反向请求分发。转发审批前必须唯一匹配活动线程，携带轮次身份时同时匹配。缺少归属的审批拒绝。全局通知由进程层消费，不能作为会话完成证据。
- 正常完成只释放当前轮次。预测复用原线程连接，由执行接管前取消或等待，禁止为了预测另开同线程 writer。需要跨进程接管时，以旧进程确认退出或原生协议确认释放为依据。单个轮次的操作不得误终止其他会话。
- 进程异常退出后按受影响线程核对，原消息回执继续可查。任务可能已发出时可以核对终态，不能自动重放。新请求按需重建并恢复原线程。

## 当前实现

连接已拆出，现有 VibeCoding 轮次仍以独占模式调用。不同原生线程的共用连接路由由本机协议夹具验证。常驻进程、预测与跨进程恢复尚待接入和验收。

Windows 隔离目录中的原生 0.171.0 实测表明，一次握手可以装载两个不同工作目录的线程，并由 `thread/loaded/list` 同时查到。刚创建且未执行首轮的线程虽然已经装载，`thread/resume` 仍可能返回 `no rollout found`。因此常驻层必须区分「当前进程已装载」和「可从磁盘恢复」，不能把两者当作同一个状态。本探测没有发送模型任务。
