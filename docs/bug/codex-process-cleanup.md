# Codex App Server 轮次收尾证据

## 现象与诊断边界

轮次完成后仍等待进程退出，10 秒后触发 `CODEX_APP_SERVER_CLEANUP_TIMEOUT`。这是进程收尾超时，不是 MCP 请求超时。启动链为 Node 启动器、原生 Codex 和工作子进程。当前尚无运行证据确认具体滞留进程；不能把关闭输入失败或某一子进程滞留当作已确认根因。

## 本次修正

- 等待 `close` 或退出且输出流已关闭，不仅凭主进程退出码释放。
- 超时移除监听，避免重复等待留下监听器。
- 保持自然退出等待和强制清理顺序，不提前释放原生 thread 写入权。
- 超时前记录 PID、退出码、信号、管道状态及 Windows 子进程 PID/父 PID/名称。清理完成记录方式与总耗时。
- 进程清单最多 64 项、16 层，查询最多 1.5 秒；采集失败记录不可用，不阻断清理。不记录命令参数、环境、Key 或对话正文。

## 维护定位

通过 Sidecar 的标准错误日志查找 `codex_process_cleanup_timeout`，按 `sessionId` 和 PID 关联 `codex_process_cleanup_complete`。前者表示等待超时，后者说明 natural/forced 和耗时；未出现完成记录不能认定写入权已安全释放。正常收尾同样记录完成事件以建立耗时基线。日志保留周期沿用受管服务日志配置。

当前采集是超时当刻快照；若主进程已退出，重新归属的子进程可能无法追溯，空清单不证明没有滞留子进程。非 Windows 暂只记录进程和管道状态。

## 已退出进程的阻断恢复（2026-10-14）

会话 `6430832c-9302-418c-bafe-70d06c6b7c5b` 已空闲，报错 PID 30344 在操作系统中不存在，新消息仍被旧收尾记录拦住。现有生命周期仅消费 `close`，而 Node 的 `exit` 与输出管道全部关闭是两个事件；继承的输出句柄可使后者延后。具体遗留句柄持有者仍未确认。

当前安装的 Codex Node 启动器在原生子进程 `exit` 后镜像其退出码。生命周期因此接受数字退出码作为该启动器的退出证据，唤醒当前等待并同时清除 session/thread 两个阻断别名；后续核验也重新读取已保存的退出码。信号退出、进程仍在运行或状态未知时仍等待 `close`，不会仅因 PID 查询失败、超时或已发送停止信号就放行。这个约束依赖当前启动器的镜像行为，升级启动器时须复核。

`codex_process_exit_confirmed` 记录 PID、退出码、信号、两条输出流状态及释放依据，不包含参数、凭据或对话；原超时与清理完成日志保留。退出证据只证明可以继续会话，不把失败轮次改为成功，也不自动重新发送队列。

回归覆盖无 close 的退出、后续重查退出码、真实启动器带有限子进程退出，以及存活/未知状态继续阻断、别名和授权隔离。Windows 真实样例未重现继承管道滞留，无 close 的边界由事件夹具验证，不能把样例当作现场根因复现。TypeScript 编译与定向测试结果见本次提交。未重启服务，原会话恢复须在用户确认加载版本后验收。
