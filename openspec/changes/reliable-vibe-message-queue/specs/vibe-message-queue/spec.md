## ADDED Requirements

### Requirement: 服务端持久队列续发
系统 SHALL 在队列入库后唤醒调度，并有界巡检；上一轮成功收口后按序发送下一项，不要求浏览器在线。发送前 SHALL 持久认领并保留原文，完成后原子收口。

#### Scenario: 入队恰好晚于完成通知
- **WHEN** 上一轮已正常完成且此后消息成功入队
- **THEN** 服务端唤醒或巡检发出队首，不等待新的浏览器完成事件

#### Scenario: 重启或完成通知丢失
- **WHEN** Java 恢复且 Sidecar 有匹配轮次的完成回执
- **THEN** 对账后恢复准入并续发，重复巡检不新建第二个执行轮次

### Requirement: 原任务收尾和用户确认
系统 SHALL 在普通开发任务的原轮收集完成状态，并保持引擎终态与任务结果的判断边界。任务未完成、需要方案或授权确认、或缺少匹配的回执时 SHALL 保留原文和队列位置，暂停自动派发。后台只能只读核对，不能追加模型轮次来询问或执行。

#### Scenario: 回答完整或任务已收尾
- **WHEN** 原轮安全收口并报告已回答或已完成
- **THEN** Forge 按既有准入条件继续队列，模型回执不会替代独立验收或授予权限

#### Scenario: 已结束但原任务仍待处理
- **WHEN** 原轮报告未完成、需要用户确认或无法证明任务结果
- **THEN** 展示对应状态、保留提交原文及关联队列，刷新和重复巡检均不会开启新的模型轮次

#### Scenario: 用户回来确认完成
- **WHEN** 用户确认原任务已经处理完成且真实引擎空闲、任务版本未变
- **THEN** 收口当前任务并恢复原队列；仍运行或等待授权时拒绝强行推进

### Requirement: 重复与未知状态保护
系统 SHALL 按稳定 turnId 去重，不因断线、超时或回执裁剪重做已执行操作。明确取消、待授权和后台任务 SHALL 阻止未经用户确认的继续执行及续发。

#### Scenario: 回执证据代际变化
- **WHEN** 查无记录但持久回执代际与派发时不同
- **THEN** 不把原任务按未执行重放，在空闲后保留原任务并等待用户核对

#### Scenario: Sidecar 明确拒绝接收
- **WHEN** Sidecar 明确拒收队首派发且尚无接收回执
- **THEN** 保留队首和原轮次标识，只在引擎确认空闲、回执代际相同且查无接收记录后有界重投
- **AND** 不调用模型去追问一条未开始的消息是否完成，不允许把它确认为完成来跳过

#### Scenario: 状态巡检遇到正在派发的轮次
- **WHEN** Java 正在登记并发送新轮次
- **THEN** 巡检在派发临界区结束后获取轮次标识，在锁外查 Sidecar，并在应用结果前再次确认轮次及状态未变

### Requirement: 轮次回执隔离
系统 SHALL 在重连时按稳定 turnId 核对当前回执，不根据旧轮、旧自动追问或迟到的状态响应推进队列。升级时已在途的旧核对可以收尾，结果不得自行推进后续任务。

#### Scenario: 恢复旧核对回执
- **WHEN** 升级后查到旧版自动追问的终态
- **THEN** 保留原任务供用户核对，重复查询不发起新轮次，也不自动派发队首

### Requirement: 原生状态与失败恢复
系统 SHALL 按当前根会话和轮次接收引擎原生状态，展示等待操作、自动重试及收口；失败结果 SHALL 使用结构化证据分类，无证据时保留未知。恢复动作 SHALL 保留当前对象及权限边界，复用现有草稿、配置和发送入口。

#### Scenario: 空闲与结果乱序
- **WHEN** Claude 原生 idle 先于或晚于结果到达，或 Codex 在本轮清理前报告 idle
- **THEN** 保留活动轮门禁，直到原生命周期完成清理；子 Agent 和旧轮事件不能覆盖当前状态

#### Scenario: 自动重试与终态失败
- **WHEN** 原生报告可重试错误，或最终结果携带失败代码
- **THEN** 前者保持运行并仅显示已提供的重试次数；后者显示明确失败类别，不冒充成功或据此释放队列

#### Scenario: 用户恢复最新失败任务
- **WHEN** 最新失败轮需要恢复且没有更新的用户任务
- **THEN** 按类别显示实际支持的恢复入口，压缩和重试提示只写草稿；显式继续仍经过现有发送门禁，忙碌时不可发送，公开评审不泄露技术分类
### Requirement: 发送原文可恢复

系统 SHALL 在清空输入框和提交发送、补充或排队请求前，将消息原文及已上传附件引用保存到按用户和会话隔离的本机恢复记录。

#### Scenario: 引擎启动失败或连接结果未知
- **WHEN** 用户已提交消息，而引擎在写入原生历史前失败，或浏览器未收到送达回执
- **THEN** 刷新后仍可从发送记录查看原文及已知状态，并复制或恢复到当前会话输入框；不能把未知当作未执行后自动重放
- **AND** 服务端已接收只表示接收请求，不能声称任务完成

#### Scenario: 本机存储失败
- **WHEN** 保存恢复记录失败
- **THEN** 保留输入和附件，提示未发送，不提交新的请求
### Requirement: 普通开发消息先在服务端接单
普通开发消息 MUST 在响应接收成功前持久保存原文、附件引用及稳定消息 ID。切换会话或关闭观察连接 MUST NOT 撤销已接收的派发工作。服务端 MUST 保留失败及结果未知记录，重启不得自动重放未知消息。

#### Scenario: 收到回复前切换会话
- **WHEN** 用户提交消息后切换到另一会话
- **THEN** 接单和派发保持提交时的会话身份，返回后能查询原文及状态

#### Scenario: 新消息遇到已登记的活动轮次
- **WHEN** 普通开发消息已接单且会话已有持久轮次，Java 正在执行或 Sidecar 仍有活动轮次
- **THEN** 保留同一消息 ID 和附件，将接单状态与队列原文一同提交，等待安全放行
- **AND** 迟到的旧结果只更新自己的发送记录，不停止当前轮次或释放队列

#### Scenario: 派发前的状态查询短暂超时
- **WHEN** 普通开发消息已落盘且派发前无法确认 Sidecar 状态，但连接仍在线
- **THEN** 在会话锁外最多补查一次状态，获得可发送状态后按原消息 ID 派发
- **AND** 仍无法确认时保留原文和未发送原因，不执行任务或自动重发

#### Scenario: 重复提交与引擎异常
- **WHEN** 同一 sessionId 和 messageId 被重复提交或引擎启动失败
- **THEN** 不重复派发、不覆盖原文，失败原因与恢复入口保留在原会话
