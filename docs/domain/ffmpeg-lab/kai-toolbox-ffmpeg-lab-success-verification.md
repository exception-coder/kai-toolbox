## 业务定义

一次转码"成功"与否，不能只凭"转码进程正常退出（退出码为 0）且产物文件已生成"来判定，还需要区分方案类型分别校验：

- **对浏览器"原生播放"类的产出方案**（即 Remux 直封装、Progressive 全转码这两种）：转码流程结束后，系统会对**产出文件本身**再做一次媒体探测，只有确认这个产物"浏览器可原生播放"，才最终判定为成功；否则即便进程正常退出、文件也确实生成了，也判定为**失败**，并提示改用 Progressive 全转码兜底。
  - 存在这条规则的业务原因：某些"看起来拷贝成功"的封装（比如把非标准编码直接原样拷贝进目标容器），进程退出码是 0、文件也生成了，但浏览器实际无法解码播放——这是一种"假成功"，必须靠对产物再验证一次才能识别出来。
- **对 HLS 类产出方案**：不适用上面这条二次校验（HLS 播放走专门的播放器组件加载分段清单，没有"是否原生可播放"这个判定维度），只以进程正常退出、主产物（播放清单文件）存在与否作为成功判定。
- **对 MJPEG 流式方案**：由于是边转边出、不落临时文件，成功判定为"客户端在流传输过程中没有提前断开连接、转码进程正常退出、且已产出字节数大于 0"；客户端主动断开（如用户关闭了预览）属于预期情况，按失败记录但不视为异常。
- **硬性运行超时**：任何一次转码运行都有总时长上限（600 秒），超过会被强制终止进程并直接判定为失败，同时提示可通过缩短截取时长重试。

## 适用范围 / 边界

- 二次校验（对产物重新探测确认"原生可播放"）**只适用于 NATIVE 播放类方案**；HLS 类和 MJPEG 类各有各自独立的判定口径，不套用这条规则。
- 该规则与"转码模式的编码/封装选择规则"是配套关系：选择规则解决"探测阶段预判要不要走这个方案"，本规则解决"方案跑完之后到底算不算数"。
