## 业务定义

配置中心一次保存操作，通常是对"同一个配置块"里的多个配置项一起改。这条规则约束的是：**这批改动只能整体成功或者整体失败，不允许出现改了一半、另一半没改成功的中间状态**。

具体的判定逻辑：保存前，系统会把这批新值连同该配置块里其它没改动的值一起，尝试组装成这个配置块本该有的完整结构（比如数值型的项必须是能解析成数字的值，列表型的项必须是合法列表，等等）。只有整体组装成功，这批覆盖值才会被正式保存并对外生效；只要有任意一项无法组装成合法值，这次保存请求就整体判定失败，之前已经在内存里试探性改动的部分会被撤销复原，回到保存前的状态，同时给出报错说明具体哪里不合法。

这条规则的业务意义在于防止"半失效配置"进入运行环境——如果允许部分成功，可能出现"这个配置块里 3 项改成功了，第 4 项因为格式错误没生效，但系统某个依赖了这 4 项组合逻辑的功能却因为不完整的配置组合而出现意料之外的行为"，这类问题很难排查。整体校验通过才生效，保证配置块任何时刻要么是"改动前的完整旧值"，要么是"改动后的完整新值"，不会停留在中间态。

## 适用范围 / 边界

- 成立范围：所有通过配置中心界面/接口发起的"保存覆盖值"操作，不管一次改了几项。
- 不适用：不校验"业务上是否合理"（比如超时时间设置成一个很离谱但类型合法的数字），只校验"类型/结构是否能被正确解析装配"；业务含义层面的合理性由使用者自行把关。
- 特例：单独的"重置某配置块"（清空覆盖、恢复默认）操作不经过这条整体校验，因为它是"删除覆盖"而不是"写入新值"，天然不存在类型不合法的问题。
