## 业务定义

三类归一化都是纯规则计算，不依赖 LLM，目的是把"人写的、格式各异的原始文本"转成"可以直接做相等比较的匹配键"：

**1）手机号归一化**
- 输入：原始手机号文本（可能含空格、括号、国家码等）。
- 规则：去掉所有非数字字符，只保留数字；如果结果以"86"开头且长度大于 11 位，再剥离这个国家码前缀（视为 +86 的残留）。
- 输出：一串纯数字。若输入为空或无有效号码，归一化结果为空串，代表"不参与匹配"（不会被误判为与另一个空号码匹配上）。

**2）公司名归一化**
- 输入：原始公司名文本。
- 规则：先把全角字符转成半角（含全角空格），去除所有空白并首尾去空格；然后依次剥离一批对匹配无意义的通用后缀/修饰词（如"股份有限公司""有限责任公司""有限公司""(中国)""集团""公司""企业""厂""店"等）。繁简转换当前不处理。
- 输出：剥离噪声词后的公司名核心部分，作为公司名匹配键。

**3）地址归一化——只取"城市+区"粒度**
- 输入：原始地址文本（详细到门牌号也可以）。
- 规则：
  1. 先做全角转半角、去空白处理；
  2. 提取"城市"：北京/上海/天津/重庆四个直辖市直接按名字提取（无需"XX市"后缀）；其他城市则在"省/自治区/特别行政区"前缀之后，锚定提取"XX市"里的 XX，避免把省名尾字错误并入城市名；
  3. 在城市之后的剩余文本里，提取"区/县"：识别"新区/高新区/经济技术开发区/经济开发区/经济区/开发区/区/县/旗"等后缀，取其前面的地名；
  4. 把城市和区拼接（如"广州天河""深圳南山"）作为归一化结果；
  5. 如果按上述规则解析不出城市或区，兜底策略是：去掉开头的省份前缀后，截取原始字符串前 8 个字符。
- 有意舍弃街道、楼号等更细粒度信息——地址软匹配只需要"城市+区"这个粒度就够用，粒度更细反而容易因为门牌号书写差异导致本该匹配的地址被误判为不匹配。

## 适用范围 / 边界

- 这三类归一化的结果是后续"确定性匹配"层判断是否命中客户库/竞品名单的直接依据（见「匹配优先级与置信度赋值口径」），归一化本身不做任何身份判断。
- 地址归一化只服务于"软匹配提示"场景（不构成定论），因此刻意选择了较粗的"城市+区"粒度，不适合用于需要精确地址比对的场景。
- 归一化规则是纯文本处理，不依赖外部服务，因此必须在所有需要做匹配键计算的地方（无论是哪个语言/脚本实现）保持逻辑完全一致，否则会出现"同一个人在不同入口被识别为不同匹配结果"的问题。
