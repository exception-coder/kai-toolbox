## 业务定义

下载任务按分片并行下载，系统会在运行期间动态收紧并发度（只降不升），治理口径如下：

- **失败率触发的降级**：
  - 维护一个滑动窗口，统计"最近完成的分片数"与"最近失败的分片数"。
  - 每当窗口内**完成分片数达到 4**、或**失败分片数达到 2**，触发一次评估；两次评估之间至少间隔 **10 秒冷却**，避免频繁抖动。
  - 评估时若**窗口失败率 > 50%** 且**当前有效并行度 > 1**，则把有效并行度**砍半**（向下取整，最低保留 1）。
  - 每次评估结束后，无论是否触发降级，窗口计数都清零，重新开始下一轮统计。
  - 降级是"永久占用"式的：本次任务运行期间不会自动恢复到更高并发；用户想要更高并发只能重新创建任务，从默认并发度重新开始。
- **HTTP 429（服务端限流）触发的降级**：与上面的失败率窗口是两条独立路径——
  - 单个分片下载命中 429 时，不计入失败率统计，而是**立即**把当前有效并行度砍半；
  - 该分片状态重置为待重试（不消耗其失败重试次数），短暂延迟（约 2 秒）后重新调度下载。

## 适用范围 / 边界

- 该套并发治理只在任务处于"下载中"状态时生效。
- 任务暂停或结束后，自适应状态（滑动窗口、已砍并发度）随任务运行时上下文一起释放，不跨任务、不持久化到下一次任务。
- 与"单个分片下载失败后允许换链路（主/备）重试"是两回事：换链路重试解决的是"这一片走哪条路"，本规则解决的是"整体并发要不要收紧"。
