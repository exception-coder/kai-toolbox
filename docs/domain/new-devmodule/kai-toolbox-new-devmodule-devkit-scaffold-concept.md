## 业务定义

"devkit" 指 kai-toolbox 对"门控开发工作台"这件事沉淀出的一套**公共骨架 + 项目差异项**的构成模型，而不是某一个模块的私有实现。任何一个目标项目要接入 kai-toolbox 做需求开发，都被规范化为同一种构成：

- **公共骨架（跨项目复用、不因项目而变）**：
  - 工作目录选择——从已配置的工作区里选一个作为本次改动的落地目录；
  - 服务启停 + 前台日志——起停该项目的本地服务并实时看控制台输出，供改完之后验证生效；
  - 一键投喂——把"目录 + 模块/需求"拼成标准触发语，转交给统一的会话运行时执行。
- **项目差异项（按项目单独确定，不复用）**：
  - 启动/停止命令（如目标项目是 Maven 服务、npm dev、还是其他脚本）；
  - 端口与就绪判定（一条命令拉起几个子服务、各自用什么端口判断"起好了"）；
  - 调试必备的额外配置（如目标业务系统的库连接、应用登录态等，因项目而异，未必每个项目都需要）；
  - 触发 AI 时用哪个"大脑"（是复用某个已有的领域自动开发技能、新写一个项目专属的，还是先用通用门控、暂不接专属技能）。

这套骨架被显式识别为一种**可生成的范式**：存在一个专门的模块，其唯一职责就是"访谈用户要接入的新项目的差异项，然后生成一个新的门控前门模块"——生成物本身就是又一个具备上述公共骨架的前门模块。这说明"门控开发工作台"不是某个模块偶然长成的样子，而是 kai-toolbox 主动认定并持续复制的产品范式。

## 适用范围 / 边界

- `new-devmodule` 本身就是这个范式的**生成入口**：使用者在此填新项目的差异项，产出一个新的前门模块。
- 已落地的复用者：`erp-dev`、`kai-dev`、`project-workspace`、`srm-dev`——都是同一套骨架 + 各自差异项的具体实例。
- 边界：`claude-chat`/`claude-chat-stable` 不是这个范式的实例，它们是被所有前门模块共同投喂、承载真正执行与关卡确认的会话运行时，不生成自己的"差异项"。
- `welfare-sign-demo` 也不属于这个范式——它是一个独立的免登录演示功能，不做"选目录接入某个外部项目做需求开发"这件事。
- 特例：并非每个前门模块都需要全部差异项——例如工具自身开发场景可能不需要额外的调试配置项，也不需要接专属大脑（用通用门控即可）。

## 备注

- 口径来源：kai-toolbox 代码调研起草（对比 `erp-dev`/`kai-dev`/`project-workspace`/`srm-dev` 四个已落地前门模块的构成，以及 `new-devmodule` 页面对"差异项"的显式收集），待 owner 核实。
- 易混点：不要把"devkit"理解成某一段具体代码或某个类；它是"公共骨架 + 差异项"这套构成模型本身，换一套技术栈重新实现，这套构成划分依然成立。
