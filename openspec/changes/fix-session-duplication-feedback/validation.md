### 问题证据与修改

- 截图“复制结果尚未确认”来自 `useClaudeChatSocket` 的固定 15 秒计时；普通复制仅在收到不同源 ID 的 Ready 时确认成功。后端 `duplicateSession` 先落库，再 `startSession`，没有独立创建回执；引擎能力准备和传输延迟都会进入复制等待。
- 已发送的复制不随 WebSocket 重连重发，原实现又没有持久请求编号、查询结果或原子事务，不能可靠区分已创建、回执丢失和部分落库。运行日志不足以证明截图中那一次复制是否已创建，未通过标题或列表顺序猜测，也未再次复制真实用户会话。
- 普通复制改为登录态 HTTP。副本、Auth 链路、附加目录和回执在同一 SQLite 事务提交；按用户和请求编号复用结果，服务重建不丢回执，副本被删除时不自动重建。
- 浏览器先保存编号，失败最多三次同编号核对；未知状态可直接“继续核对”，无需翻列表。刷新后的再次操作仍用原编号，离页后的迟到结果不抢回视图，且不清除未展示结果的编号。复制创建成功后才独立连接引擎，连接错误不改写创建结果。Auth 切换保留原协议，不在本次声称具备同等恢复能力。

### 原因与实现

普通复制原先也使用源会话的 Auth 链路。同目录的唯一关联已由源会话占用，新副本插入后关联失败，会被删除并返回源会话；前端等待不同于源 ID 的 Ready，最终超时。菜单关闭后复制状态消失；最近会话未传入复制动作。

普通复制明确传 `reuseAuthSession=false`，独立链路并继承源 Auth；携带交接包的 Auth 切换传 true，沿用已有链路复用。旧消息缺省继续兼容旧语义。进度弹窗独立于列表，成功以新目标 Ready 确认，未知结果提示先检查列表；已发送的复制不随断线重发。
