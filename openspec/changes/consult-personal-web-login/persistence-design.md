# 用户个人账号持久绑定

## 目标
账号按Forge用户与系统保存，同一用户后续咨询复用，无需每15分钟重新填写；每个用户在每个系统保留一个当前账号，修改站点/环境/账号替换原绑定。只读和非生产边界保留，2026-11-18取消个人站点的资源登记及项目定位前置要求。

## 设计
复用common的ResourceCredentialCipher（ops实现AES-GCM、独立密钥），fore-consult独立表fore_consult_personal_web_account保存绑定。唯一键owner_id/source_path，随机id用于模型引用；SQL参数化，密码仅密文入库，响应不包含密文或密码。模型从服务端咨询所有者及系统查找绑定，不能传用户ID替换身份；管理员不豁免。GET仅查本地元信息和上次检查时间，不拿浏览器全局锁；账号操作使用有界条带tryLock，忙则409，不拖住状态查询。

绑定持续到本人解除，不等于Cookie永久有效。浏览器context仍15分钟释放；重新读取自动创建隔离context。已成功登录的context遇到可见密码框/HTTP401时关闭并重登一次；失败新context不递归重试。登录失败状态持久记录，后续自动读取停止尝试，用户显式“检查登录”或更新密码才重试。绑定保存、上次检查、实际读取成功分别显示；超过60秒的READY元信息标待检查，GET不宣称当前在线。显式检查复用现有站点/环境验证，每次读取仍走完整网关边界。

保存入口替换旧临时授权行为；退出改为解除绑定并释放context，影响本人该系统后续咨询。旧内存授权不自动保存密码，重启后用户首次重新绑定。前端沿用60秒超时及结果未知恢复，密码不回显，不写聊天或localStorage。按OBJ-01/CTX-01/FEED-01/CTRL-01/IDEM-01，状态查询与检查动作区分，不增加新导航，不将个人账号加入公共资源目录。

## 2026-11-18 个人站点直接使用

个人账号表单用于可选保存。已绑定站点使用 `consult_web` 的账号引用。本轮有适用绑定或已装配公开链接独立浏览器时关闭宿主浏览器；直接登录另一个没有匹配绑定的站点时，仍需用户明确授权，并遵守本轮宿主能力和已配置审批。SDK 允许已授权登录和只读请求，禁止业务写入及从网页取得授权。使用者主动发送的原始聊天予以保留，Agent 不得复述凭据或输出登录载荷、Cookie。真实浏览器能力按轮验证，部署进度见[咨询网页验收](../consult-browser-navigation/tasks.md)。

本人表单填写的HTTP(S)地址是个人访问目标，不再要求discoverBound成功；RFC1918内网与自定义端口允许使用。公共目录仅用于保留已知生产/未知环境冲突检查及原已登记站点规则，不要求当前系统登记。未登记的回环、链路本地、组播、未指定地址及共享保留网段仍拒绝。模型只能选择本人已有personal-引用并读同源路径，不能自行扩大目标。

fore-consult保存入口取消源码焦点前置检查；签名Web DISCOVER把个人账号与公共发现分开，公共项目未定位/未登记时仍返回个人账号，个人READ在公共路由校验前分流。公共READ及数据库路径不变。用户/系统仍是已有账号保存分区，尚未提供跨系统账号列表或多站点管理，不引入数据库迁移。

采用现有URL/地址解析和隔离浏览器，不另造登录框架。参考[OWASP SSRF防护](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)的明确目标与保留地址检查；本次明确允许用户指定业务内网站点，不把“必须公网”误作所有业务场景的统一规则。既有浏览器仅限制跨源导航，不宣称具备网络层完整隔离。部署与真实应用验收单列。

依据：Playwright官方认证文档 https://playwright.dev/java/docs/auth 明确登录态包含敏感Cookie/存储且有独立生命周期；复用隔离context，不持久导出明文storageState。

DDL核验为DDL_MISSING（新增表；扫描上限），Forge资源绑定为空；本次只在隔离SQLite测试执行新幂等脚本，不操作运行库。既有AI架构中的个人账号边界同步为用户系统绑定，业务全景能力不变，仅细化账号生命周期。

## 2026-11-17 传统登录页兼容修复

截图中的“已保存但未登录”有实际适配缺陷：ERP公开登录页的输入区域绝对定位，外层form高度为0；真实Chromium观测到可见密码框1个、所属form1个，但旧选择器 `form:has(input[type=password]):visible` 返回0。因此原实现退回body范围，未记录 `/j_spring_security_check` 表单action，该端点也不符合SPA通用登录端点匹配，会被只读请求边界拦截。改为 `form:has(input[type=password]:visible)`，仍要求唯一表单及输入框，沿用原同源登录许可，不放开业务写操作。

第二个根因：该站点默认 `/` 始终展示登录页，登录成功后落点为 `/index.jsp`。原实现成功后再次导航默认入口，重新看到密码框并误判失败。真实实现直连 `/index.jsp` 返回READY，而默认 `/` 返回WAITING_LOGIN。修复为请求路径与登录路径相同且已到达其他同源路径时，重新读取实际落点检查登录；显式其他业务路径仍按请求导航，失效检查仍执行真实读取。

按FEED-01，界面区分尚未登录和历史待检查，并说明保存账号可直接检查；删除没有证据的验证码/单点登录归因。此为已有能力的兼容修复，无AI编程架构契约或数据库变更。初次独立浏览器直连提交等待超时，后续真实实现已验证目标站点登录落点READY；最终默认入口验证和同事部署验收分别记录。
