## 业务定义

实验台对同一个源文件提供 5 种"转码/封装出 web 播放"方案，探测预览阶段与实际执行阶段使用同一套判定规则，保证"页面上预判的效果"就是"真正执行的效果"。各方案的选用与参数口径：

- **Remux 直封装**：只换容器、不重新编码。仅当源视频编码与源音频编码**都已经**是可以直接原样拷贝进目标容器的类型时，才预判为「可行」；只要有一路不满足，就预判为「预期失败」——用来演示"为什么单纯换容器行不通"。这是 5 种方案里**唯一会给出失败预判**的方案。
- **Progressive MP4 全转码**：不判断源编码，统一重新编码为通用的浏览器原生播放格式，作为万能兜底。重编码时有两条附加规则：①若源画面尺寸过小（低于最小可播尺寸），先按原比例放大到最小可播尺寸再编码，避免部分编码器对超小帧的限制，同时强制宽高为偶数；②音频统一重采样到标准采样率，避免个别低采样率源在编码时报错。
- **HLS（MPEG-TS 分段）**：视频流与音频流**分别独立**判断是否可以直接拷贝——哪一路源编码兼容就直接拷贝，不兼容的那一路单独重新编码，两路不要求同步处理。
- **HLS（fMP4/CMAF 分段）**：不做按流判断，视频、音频**统一强制重新编码**。原因是这类分段格式的分片元信息如果与源参数不一致会导致播放器加载失败，所以稳妥起见现代封装一律走重编码，不冒险尝试拷贝。
- **MJPEG 帧流**：把视频抽帧编码成图像流，不含音频，是"以上方案都不可行/都不满意时，至少能看到画面"的终极兜底方案，且是唯一的"边转边出、不落临时文件"的流式方案。
- **判定结果只有三种**：可直接达成（OK）/ 预期做不到（FAIL）/ 需要转码但预期能成（TRANSCODE）。只有 Remux 会出现 FAIL，其余 4 种方案恒为 TRANSCODE。

## 适用范围 / 边界

- 以上是"探测预览阶段"的**预测口径**，用来提前告诉用户"这个方案大概率行不行"；真正是否成功，仍以实际执行结果为准（尤其是 NATIVE 播放类方案还有二次校验，见配套的成功判定规则）。
- 该套规则服务于"实验/调试"场景，刻意统一走软件编码而非硬件加速编码，与生产环境的转码路径是两套独立口径，不能相互替代验证。
