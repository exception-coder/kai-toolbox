## Context

SessionRuntimeStateService.assess 只允许 IDLE；ClaudeChatService.sendDelegatedUserMessage 已持有 ctx 锁，而 resumeCurrent 未加同一把锁。SessionRuntimeHealth 只展示一致性。

## Goals / Non-Goals

恢复已清理的中断会话，保留未知状态保护。不自动重放历史请求、不修改原生协议或停止其他会话。

## Decisions

状态服务集中判定可恢复性：Sidecar 可达、新鲜、会话存在、无活动/待确认/后台任务、Java 与持久化一致。发送在 ctx 锁内核对并将 INTERRUPTED 转 IDLE，清理旧生命周期；原 Sidecar 已空闲无需重建。显式重载也在同一锁内执行，先核对清理事实，重载后再次核对再标记空闲。相同会话请求不会交错启动。Sidecar 确认会话缺失且 Java 无任务时只允许显式重载；必须等重载后会话存在才能转空闲，发送不能直接跳过挂载。并发创建 Java 上下文使用 putIfAbsent 保持唯一锁。界面复用原重载动作，异常时提供重新检查。

Codex App Server 的 `turn/completed` 只代表业务终态，不代表 thread writer 已释放。Sidecar 必须先关闭本轮受管进程并确认进程退出，再发布允许上游释放队列的 `result`。自然退出超时后只终止本轮受管进程树并再次确认，不扫描或影响其他客户端。Java 中断协调器的超时动作只查询新鲜运行态，不再基于固定时长伪造终态；真正的 Sidecar `result` 仍是释放 Java 轮次的唯一事件。

## Risks / Trade-offs

### 中断等待与重试

适用产品原则：OBJ-01、CTX-01（按当前会话/轮次恢复）、FEED-01、CTRL-01（区分请求、等待和真实终态）、EVID-01（未知退出不宣称完成）、IDEM-01（重复终止不启动新执行）。无例外。

Sidecar 不再用 4 秒计时器缓存一个假中断结果；计时到 30 秒时重试当前引擎中断并发出 `INTERRUPT_CLEANUP_PENDING`，活动轮次仍由真实执行返回后释放。前端独立限制中断按钮的等待时间：30 秒未确认则显示恢复说明、允许再点终止，不改变 running 或放行队列。切会话、终态与卸载取消该计时，成功终态清除本次等待提示。

Codex 适配器在协议清理之后仍保留本轮受管进程的清理入口，重复终止可再次请求既有进程控制器清理该进程。此入口只接受当前持有的会话记录，不枚举或停止其他会话；确认退出、异常返回和 writer barrier 继续沿用现有门禁。终止发生在成功结果已缓存但尚未发布时，将最终结果改为 interrupted、禁止释放队列，不丢弃 usage。其他引擎保留各自中断能力；无法确认清理时只提供重试，不承诺强制成功。

当前证据：截图对应的 ERP日常需求持久状态仍为 RUNNING；源码证明旧计时器不会结束未返回的执行、重复 abort 不重新清理、前端无等待上限。未取得该轮引擎完整取消日志，不能把具体底层阻塞归因于某条命令或 SDK。代码修复、隔离测试和实际运行恢复分开记录。

- 查询失败：不更改中断状态，不发送消息，保留恢复按钮。
- 恢复期间新任务：同一 ctx 锁串行发送与重载；Sidecar 最终启动仍保留现有原子门禁。
- 重载可异步完成：重载后即时查询未就绪则不声称成功，允许重试。
- 原生进程清理较慢：会延后数秒显示本轮彻底结束，但不会把下一条消息送进仍持锁的 thread。

## Migration Plan

### 传输重连丢失活动轮次（2026-10-24）

对象仍为原Forge会话及其当前turnId，沿用OBJ-01、CTX-01、FEED-01、EVID-01、CTRL-01、IDEM-01，无新增导航、权限或自动重发。截图会话 `97225761-8e1c-4fa7-aed4-7b98c1366338` 的日志在18:48:31记录原生进程正常退出，但其 `464e2e1f-51f7-44c1-94dc-c24ba3e0ac0f` 轮次的assistantDelta与result因 `currentTurn=none` 被丢弃。原生历史仍保留18:48完整回答；独立只读Sidecar快照证实当时无活动、无审批及后台任务。后续浏览器重新进入原会话后可读到18:48及18:55回复，并验证非空草稿的发送入口可用，未发送诊断消息。不能据此声称新后端修复已加载。

原 `onSidecarDown`、`resumeAllSessions` 和即时恢复入口把传输断开/重连直接等同于执行结束，清空turnId并置空闲；但SessionManager.resume保留既有Session及运行中的Agent，因而后续真实事件会失去相关性。修复保留断线时的轮次身份，由后台在ctx锁外查询新鲜Sidecar快照，避免result回调等待ctx锁而阻塞同条WebSocket的查询回包。锁内复核查询前后的turnId和状态，旧快照不覆盖新轮次或已到达的终态。

快照仍活动则保留/接回其真实turnId并维持RUNNING，不重复resume；只有无活动、无审批、无后台任务才挂载原上下文。若原RUNNING已消失则保留INTERRUPTED，原问题不重发、队列不自动释放。查询失败或缺少活动turnId时保持锁定并继续有限恢复。即时重连只恢复传输并调度同一核对流程，本次尚未接收的消息明确提示重试。已替换的WebSocket不再处理消息，避免旧连接重复投递。SDK升级调用同一恢复结果，未确认不得报告会话恢复成功；本次未执行任何升级或重启。

浏览器存在过程回复但漏收result时，也以属于本轮且可信的Runtime终态消除本地running残留；新轮启动宽限期、旧快照、过期或查询失败仍不放开发送。原生历史读取继续使用既有入口，不复制会话、不改写历史或补造答案。适用定向回归及新版本运行验收分别记录在tasks。

会话 `4a7f8d17-be72-4bac-adb4-a25182c26211` 的本轮原生记录在 14:14:38 写入完成事件；14:53:44、14:54:20、14:55:26 的中断均被 Sidecar 接受，本地轮次 `f1be8b3d-32d6-4672-9719-f897f5db6089` 持续为 active/interrupting，无待审批或后台任务。日志还存在 SDK 专用的分叉锚点读取超时；当前日志未完整记录该轮的实际传输选择和进程身份，因此不能断言已还原此次故障的全部底层条件。

已在锁定版本 `@openai/codex-sdk:0.162.1` 的真实执行器上复现：收到 `turn.completed` 后，若进程保持输出流打开，原 `for await` 继续等待 EOF。SDK 的 finally 还会移除全部 ChildProcess 监听，单靠 exit/close 监听不能保证平台取得清理回执。既有 App Server 清理记录无法覆盖 SDK 所有的原生进程。

修复落在 Sidecar 引擎适配层：SDK 事件迭代在成功或失败终态后返回，触发 SDK 自身 finally；通过 [Node 子进程诊断通道](https://nodejs.org/api/diagnostics_channel.html) 与 AsyncLocalStorage 仅捕获当前 SDK 调用创建的 exec 进程，不改写 SDK 私有对象或全局 spawn。诊断通道缺失或未捕获进程时拒绝声明成功。SDK 清除监听后定期复核退出属性；只有直接启动的 SDK 原生二进制可按 signalCode 确认退出，Node launcher 仍保留原有退出判定。确认原生退出后给缓冲输出短暂排空时间，再结束平台持有的读管道，不以此终止后代进程。

成功结果暂存到进程退出确认后才发布；取消覆盖未发布的成功并暂停队列。退出未确认时保留会话及原生 thread 的 writer barrier，不在固定时间后伪造空闲。停止重试同时覆盖 App Server 与 SDK 的本会话进程；新建原生 thread 后同步退出门禁所用身份，避免新会话遗漏别名保护。未新增数据库写入或迁移。

隔离回归与当前真实会话恢复分开验收；当前服务仍加载旧版本，需用户确认后经 `node forge.mjs` 加载新 Sidecar，并按实际会话检查停止、队列与稳定观察。
