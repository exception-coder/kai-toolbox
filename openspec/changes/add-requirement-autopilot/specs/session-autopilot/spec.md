## ADDED Requirements

### Requirement: 需求驱动的有界自动监督
系统 SHALL 提供 REQUIREMENT_BEST_EFFORT 模式，允许用户在原开发会话直接提交需求与预期结果，无需先手动选择 OpenSpec。系统 SHALL 复用现有持久监督、内部续跑队列、进度回灌及预算控制，不改变默认 OPEN_SPEC_STRICT 行为或项目写入与运行权限。

#### Scenario: 无规格需求启动并重复提交
- **WHEN** 用户选择需求持续推进，提交有效需求与监督预算
- **THEN** 系统绑定当前会话真实项目并持久化运行，事务提交后派发执行
- **AND** 同项目同需求的活动运行重复提交复用原运行，其他目标不得覆盖活动运行
- **AND** 不以需求运行编号读取、创建或归档 OpenSpec，不安装严格执行 Skill

#### Scenario: 跨轮继续与断线恢复
- **WHEN** 需求运行活动中，引擎成功收口并仍有未完成工作，或后台巡检发现未排队的空闲活动运行
- **THEN** Runtime 在原会话按 run、generation 与轮次幂等排队，交接目标、预算及已有进展
- **AND** 旧 generation、暂停或预算耗尽的消息不能领取，不依赖页面保持打开

#### Scenario: 连续无进展与预算耗尽
- **WHEN** 多轮缺少报告或没有新增证据，达到无进展上限，或轮次/时间预算耗尽
- **THEN** 系统暂停派发并展示原因，保留成果与恢复入口
- **AND** 同一证据的重复报告不重置无进展次数；重置预算须沿用用户显式版本化动作

#### Scenario: 完成报告与严格验收区分
- **WHEN** Agent 报告 COMPLETE
- **THEN** 系统要求非空摘要、非空验证证据和显式空 remainingWork，否则拒绝完成报告
- **AND** 仅成功且安全收口后记录 Agent 自验完成，保留证据供复核，不宣称 OpenSpec 严格验收通过或已部署

#### Scenario: 需要人工授权或用户接管
- **WHEN** 用户手动接管，或 Agent 报告需要授权、真实阻塞或失败
- **THEN** 系统按原监督状态契约停止自动派发，保留报告、原因与恢复操作
- **AND** 本模式不自动授予服务重启、生产、发布、写入或额外资源权限

### Requirement: 原会话中选择监督方式与查看报告
系统 SHALL 在既有自动推进覆盖层提供按规格推进和需求持续推进选择，保留会话上下文及预算、报告和恢复入口，不新增导航。

#### Scenario: 草稿与失败恢复
- **WHEN** 用户关闭弹框、切换方式或提交失败
- **THEN** 同会话需求草稿保留，失败可重试，提交期间防重复操作
- **AND** 换会话清空旧输入，手机可滚动到发送操作，关闭后可返回原会话操作

#### Scenario: 查看需求监督状态
- **WHEN** 用户查看需求运行的摘要、推进详情或全局看板
- **THEN** 系统展示需求模式、目标、轮次、原因及可用报告，不显示虚构规格任务百分比
- **AND** 完成明确标为 Agent 自验并提示复核，与原严格规格完成区分
